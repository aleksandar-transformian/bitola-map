# Анализа: каде оди времето при рендерирање

Датум: 2026-11-11 · основа: commit пред фаза Б · мерено во headless Chromium (SwiftShader) за
структурата + пресметка за референтниот уред. Времињата на вистинскиот уред **ги нема уште** —
ги дава првото `?bench` мерење на MacBook-от (протокол во `plan.md`); тогаш оваа анализа се
дополнува и приоритетите се потврдуваат.

## 1. Референтен уред

MacBook Pro 15" (2018/19): i7 6 јадра 2.2 GHz, **Radeon Pro 555X 4 GB** (GDDR5, 128-bit ≈ 80 GB/s,
≈ 1.3 TFLOPS) + Intel UHD 630, 16 GB, Retina 2880×1800.

- **Пиксели:** Chrome преку цел екран со „Default“ скалирање (изглед 1440×900) е ≈ 1440×790 CSS
  пиксели × DPR 2 = **2880×1580 ≈ 4.5 MP**; со „More space“ (1680×1050) ≈ 6.5 MP. Профилот
  `desktop` дозволува `maxPixelRatio: 2`, па цртаме 3.5–5× повеќе пиксели отколку на обичен
  1440×900 екран. Сè што чини „по пиксел“ (сенки во шејдерот, пост-ефекти, MSAA) е 3.5–5× поскапо.
- **Две картички:** WebGL бара `powerPreference: 'high-performance'`, но Chrome на macOS
  понекогаш останува на Intel UHD 630 (≈ 3–4× послаба). Извештајот го бележи GPU-то.
- **Термика:** овој модел е познат по термално забавување. Јамката сега црта **секој кадар и
  кога ништо не се движи** (60 × во секунда, постојано 100 % GPU) → по неколку минути часовниците
  паѓаат и се јавува сецкање и при мала сцена.

## 2. Структура на кадарот (сега)

„Разгледница“, десктоп, преглед — **16 повици, 4.06 M триаголници** по кадар:

| слој | триаголници | темиња | меморија (атрибути) | сенка | забелешка |
|---|---:|---:|---:|---|---|
| релјеф | 842 k | 422 k | 13.5 MB | прима | рамномерна мрежа 15 m, **без LOD**, една мрежа → без culling |
| згради | 360 k | 1 078 k | 43.1 MB | фрла + прима | една споена мрежа (20.5 k згради), **неиндексирана** → без culling |
| дрвја | 40 × 26 948 = **1 078 k** | — | — | фрла + прима | еден InstancedMesh → секогаш сите, и во сенките |
| улици | 120 k | 126 k | 5.0 MB | прима | |
| знаменитости | 96 k | 289 k | 12.7 MB | фрла + прима | неиндексирани |
| вода, пруга, бочни страни, небо | 28 k | | | | |
| **главен пас** | **≈ 2.53 M** | | | | |
| **сенки** (згради + знаменитости + дрвја) | **≈ 1.53 M** | | | | мапа 2048², PCFSoft |

- **Дрвјата се > ½ од сите триаголници** (1.08 M во сцената + 1.08 M во сенките), а на прегледот
  повеќето се помали од пиксел.
- „Макета“ на десктоп: GTAO ја црта целата сцена уште еднаш (нормали + длабочина) → ≈ 7.5 M
  триаголници и ≈ 36 повици (NOTES, фаза 3).
- Сите големи слоеви се **една мрежа** → frustum culling не помага: и на поглед од 85 m до Филип II
  се цртаат сите 20 k згради, целиот релјеф и сите дрвја (и во сенките).

## 3. Цена по пиксел (DPR 2 ≈ 4.5 MP)

| чекор | што прави | проценка |
|---|---|---|
| главен пас | Lambert + PCFSoft сенки (повеќе читања од мапата по фрагмент) + прозорци ноќе; MSAA 4× во **HalfFloat** (8 B × 4 примероци = 32 B/px боја + 16 B/px длабочина) | ≈ 220 MB MSAA цел, препишана 2–3× (overdraw) по кадар → значаен дел од ≈ 80 GB/s |
| **MSAA и во пост-пасовите** | `EffectComposer` ја клонира MSAA целта (`renderTarget2 = renderTarget.clone()`), па `output`, `postcard`, `tiltshift` ×2 пишуваат во 4× MSAA и решаваат секој пат | непотребна пропусност; поправка без промена на изгледот (Б2) |
| `postcard` | по пиксел: 3 fbm × 5 октави + 2 шума = 17 value-noise = **68 hash-функции** + 13 читања | ≈ 300 M hash/кадар → неколку ms на 555X; шумот е статичен во екранот → може да се испече (Б3) |
| `gtao` (Макета) | 12 примероци + денојзер 12 примероци, цела резолуција, + повторно цртање на сцената | најскапиот ефект (NOTES); пола резолуција ≈ ¼ од цената (Б8) |
| `tiltshift` (Макета) | 2 × 5 читања | евтино |
| `backdrop-filter: blur` | 3 панели (наслов, мени, избирач) над canvas што се менува секој кадар → композиторот повторно замаглува | не се гледа во WebGL тајмерот — аблацијата го мери преку интервалот |

## 4. CPU

- Повиците за цртање се малку (16–36) → three.js не е тесно грло на CPU.
- `labels.update` секој кадар: `getBoundingClientRect` на 5 панели **по** запишување на
  `transform` на натписите во претходниот кадар → принуден layout секој кадар + до ~60
  запишувања на стил. Мало, но постојано (Б9).
- Изградба при вчитување: ≈ 0.6–1 s (згради, знаменитости) — не влијае на сецкањето.
- Смена на стил: ≈ 340 ms за нова геометрија + компајлирање шејдери на првиот кадар (Б10).

## 5. Хипотези (по очекувана тежина на референтниот уред)

1. **Пикселите на Retina** (DPR 2) × пост-ефектите × MSAA во HalfFloat — главниот трошок на
   GPU; „Разгледница“ = `postcard`, „Макета“ = `gtao`.
2. **Постојаното цртање** (и во мирување) → термално забавување → сецкање што се влошува со
   времето.
3. **Сенките**: втор пас со 1.5 M триаголници (дрвјата!) + PCFSoft во секој фрагмент.
4. **Темињата**: 2.5–7.5 M триаголници без culling/LOD — помалку важно од пикселите на
   дискретна картичка, но пресудно ако Chrome работи на Intel UHD 630.
5. CPU (натписи, layout) — мало, но се гледа во p95 при движење.

Аблацијата во `?bench` (дрвја, згради, релјеф, сенки, пост-ефекти поединечно, DPR 1.5/1, MSAA,
blur, „минимум“) ја мери секоја од овие хипотези директно на уредот.

## 7. Измерено на референтниот уред (2026-11-12)

Извештај: `docs/perf/results/2026-11-12-b3c5119-standard-gpu-macbook-555x.json` — Chrome 157,
**Radeon Pro 555X** (ANGLE Metal; не Intel ✓), 1680×824 CSS × DPR 2 = **3360×1648 = 5.54 MP**
(скалирање „More space“), MSAA 4×.

| стил | fps (ден) | GPU ms | fps (ноќ) | GPU ms (ноќ) |
|---|---:|---:|---:|---:|
| Low-poly | 21–22 | 39–41 | 15 | 62 |
| Цртан филм | 19–20 | 41–45 | 14 | 64–66 |
| Разгледница | 15 | 60–62 | 11–12 | 82–83 |
| Бајка | 8–10 | 94–114 | 7.5–8 | 118–127 |
| Макета | 7–8 | 118–131 | 6.5 | 146–151 |

Цел: GPU ≤ 13 ms. Сите стилови се 3–10× над буџетот. **CPU е 0.6–1.5 ms по кадар — не е проблем.**

### Заклучоци

1. **Тесното грло се пикселите, не геометријата.** „Минимум“ ги црта истите 2.5 M триаголници за
   6 ms (60 fps). Сите дрвја (2.2 M триаголници) чинат само 3.7 ms (6 %); целата геометрија
   заедно ≈ 17 ms од 62. Хипотезата 4 (темиња) е **отфрлена** → culling/LOD (Б4, Б6) се со низок
   приоритет. Хипотезата 1 (пиксели × MSAA × пост-ефекти) е **потврдена**.
2. **MSAA 4× во HalfFloat е најскапата поединечна работа: 43–60 % од кадарот** во секој стил.
   Дел од тоа е непотребен (пост-пасовите пишуваат во MSAA цели): `tiltshift` (2 × 5 читања) чини
   22 ms, `grade` 11 ms — тоа е цена на целта, не на шејдерот.
3. **Пост-ефектите се второто**: `gtao` 68 ms, `bokeh` 37 ms, `postcard` 21 ms, `bloom` 20 ms,
   `ink` 11 ms — сите во полна резолуција од 5.5 MP.
4. **Ноќта чини +21 ms во секој стил** (Разгледница 62 → 83, Цртан 43 → 65, Low-poly 41 → 62) —
   тоа е `bloom` (во „Бајка“ измерен на 20 ms) во полна резолуција.
5. Сè е линеарно со пикселите: DPR 1.5 = −38 %, DPR 1 = −65 %.
6. Сенките: 9–12 ms (8–23 %). `backdrop-filter`: ≈ 3 ms од интервалот во секој стил (не се гледа
   во GPU тајмерот, како што се очекуваше).
7. **Удар при смена на стил: 0.3–3.4 s** (→ Low-poly 803 ms + 3.4 s прв кадар; → Разгледница 2.7 s) —
   компајлирање шејдери на Metal. Прв кадар при вчитување 4.65 s (буџет 3 s).

### Ограничување на мерењето

На ANGLE/Metal **GPU времето по пас не е веродостојно**: речиси сè се припишува на `scene`
(`postcard`, `ink`, `output` = 0 ms, `gtao` = 0.8 ms), иако аблацијата покажува 11–68 ms за тие
пасови. Вкупното GPU време е точно (GPU + ≈ 6 ms = интервал). За „каде оди времето“ важи
**аблацијата**, не колоната по пас (и редот „GPU … scene …“ во `?debug` на macOS).
